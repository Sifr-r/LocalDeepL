## Landscape summary (LocalDeepL-relevant)

- **OSS has converged on three pipeline patterns** for "anything→MD":
  A. local layout/ML without LLM (PyMuPDF4LLM, PDFMiner, Marker's
  plain mode); B. local + VLM post-processor (Marker `--use_llm`,
  Docling vlm pipeline, MinerU hybrid-engine, **LocalDeepL**);
  C. VLM-only (Zerox, LlamaParse). **LocalDeepL is in B-mode
  center, with the most defensible implementation** because
  `dense_mode="auto"` per-page routing + `grounded_backend`
  pluggability is a uniquely tunable knob. See
  `track-md.md` §2.2.1 (Marker) and §2.2.2 (Docling) for the
  architectural analogs.
- **No first-party cloud "anything→MD" service exists.** Azure
  Doc Intel is the strongest PDF→MD API but uses **HTML tables +
  LaTeX + `<!--PageBreak-->`** (not GFM); Google Document AI has
  **no Markdown output**; Adobe's PDF-to-Markdown is PDF-only with
  400-page/100 MB caps; Markitdown's PDF path (pdfplumber+pdfminer
  only) fails on scanned/complex PDFs (issues #296, #1361, #1845).
  See `track-md.md` §2.1 (Tier 1) for all four cloud players.
- **License posture is a real B2B wedge.** Marker's GPL-3.0 +
  RAIL-M with hard $2M revenue/funding cap ([MODEL_LICENSE
  Attachment A, datalab-to/marker]); PyMuPDF4LLM is AGPL v3 OR
  paid commercial; Pandoc is GPL-2.0+ copyleft. Docling,
  Markitdown, PDFMiner, Zerox, MinerU are permissive. See
  `track-md.md` §3.4 (license matrix) and §5.1 (direct analogs).

## Architectural references worth borrowing

- **Docling's `StandardPdfPipeline`** is the production reference
  for multi-stage threaded PDF processing: 5 stages
  (Preprocess → OCR → Layout → Table → Assemble) with bounded
  `ThreadedQueue`, per-run-id isolation, document-timeout,
  `SUCCESS/PARTIAL_SUCCESS/FAILURE` status, **failed pages
  preserved as empty `PageItem` entries** so page-break markers
  stay correct
  ([`docling/pipeline/standard_pdf_pipeline.py:393-435, 572-606, 763-823`](https://github.com/docling-project/docling/blob/main/docling/pipeline/standard_pdf_pipeline.py)).
  Cite: `track-md-evidence-oss1.md` §4.3.
  **LocalDeepL's `HybridEngine` is sequential per page** (per
  AGENTS.md). If/when batch throughput becomes a bottleneck,
  copy this pattern.
- **Docling's heavy model cache** keyed by options-hash:
  `DocumentConverter.initialized_pipelines: dict[(pipeline_class,
  options_md5_hash), pipeline_instance]`
  ([`docling/document_converter.py:355-378`](https://github.com/docling-project/docling/blob/main/docling/document_converter.py)).
  Cite: `track-md-evidence-oss1.md` §4.3.
- **Marker's DI via reflection** to wire `artifact_dict` and
  `config` into processors: `BaseConverter.resolve_dependencies`
  ([`marker/converters/__init__.py:13-39`](https://github.com/datalab-to/marker/blob/master/marker/converters/__init__.py)).
  Cite: `track-md-evidence-oss2.md` §1.5.
- **Markit's `magika` content-sniff dispatcher** (vs
  extension-based) — Markitdown uses
  `self._magika = magika.Magika()` to dispatch even without
  extensions
  ([`packages/markitdown/src/markitdown/_markitdown.py:105-109`](https://github.com/microsoft/markitdown/blob/main/packages/markitdown/src/markitdown/_markitdown.py)).
  Cite: `track-md-evidence-ms.md` §1.
- **PyMuPDF4LLM's `OCRMode` enum** (5 modes:
  NEVER/SELECT_REMOVING_OLD/SELECT_PRESERVING_OLD/ALWAYS_REMOVING_OLD/ALWAYS_PRESERVING_OLD)
  is a well-thought-out model of the OCR-decision space. Cite:
  `track-md-evidence-oss2.md` §3.5.
- **PyMuPDF4LLM's hybrid OCR strategy** — "only where it is
  actually needed"; reduces processing time by ~50%. Four
  trigger conditions: too many illegible chars, vector graphics
  simulating text, previous OCR text layer, images containing
  text. Cite: `track-md-evidence-oss2.md` §3.3. Directly maps to
  LocalDeepL's `dense_mode="auto"`.

## Product-strategy findings

- **Markdown schema fragmentation is the #1 integration friction.**
  Every vendor's Markdown is subtly different (Azure HTML tables,
  Adobe base64-embedded images, Docling DocTags, Marker GFM +
  28-element JSON). LocalDeepL can win on "predictable,
  configurable Markdown output" — but only if it explicitly
  documents its schema and provides an HTML-tables / GFM-tables
  toggle. See `track-md.md` §6.1 (gap recommendations).
- **M365 Copilot parsing is closed and not a direct competitor.**
  The real Microsoft cloud competitors are Azure Document
  Intelligence (markdown via `prebuilt-layout`) and Azure
  Content Understanding (multimodal umbrella). No public
  "Microsoft Document Transformer" arXiv paper exists. The
  closest Microsoft research lineage is `LayoutLMv3` (2022) and
  `UDOP` (CVPR 2023) — both pre-training papers, not the
  production Copilot pipeline. Cite: `track-md-evidence-ms.md` §4.
- **Markitdown is the de-facto OSS reference (153k★) but
  explicitly positions itself as low-fidelity.** README:
  "meant to be consumed by text analysis tools — and may not
  be the best option for high-fidelity document conversions for
  human consumption." This is the exact positioning LocalDeepL
  rejects. Cite: `track-md-evidence-oss2.md` §4.1.
- **Zerox's `maintainFormat` pattern** (pass prior page's
  markdown as context to VLM for cross-page format consistency)
  is worth selectively adopting for the `GroundedEngine` VLM
  post-processor. Cite: `track-md-evidence-oss2.md` §4.2.
- **MinerU's v3.3 `effort` parameter** (medium/high; image/chart
  analysis off in medium) is a clean speed/quality knob worth
  borrowing. Cite: `track-md-evidence-oss2.md` §4.4.

## Gaps recommended for LocalDeepL's roadmap (mapped to extension points)

The full gap table is in `track-md.md` §6. Top items by extension point:

- **`document_processors`**: 4 new processors — cross-page table
  merge, form extraction, audio transcription (Whisper ONNX),
  long-document strategy (sliding window / streaming).
- **`aligner`**: 2 alternative backends — `pymupdf_layout`
  (opt-in, behind closed-source license gate) and
  `docling_parse` (v6.x).
- **`grounded_backend`**: 2 new options — `maintain_format` (per-
  page context threading from Zerox) and `granite_docling` (258M
  local VLM from IBM).
- **`ocr_processor`**: fallback chain (Surya → Tesseract →
  EasyOCR) + cloud backends (Azure `prebuilt-read`, Google
  Enterprise OCR).
- **`page_preprocessor`**: format-keyed dispatch (image / audio /
  video each get their own) + image-quality scoring (8
  dimensions from Google's Enterprise OCR).
- **Output writers**: 4 new — `xlsx_writer`, `html_writer`,
  `jats_xml_writer`, `chunks_writer`; plus a Mammoth-style
  `style_map` DSL for the existing `docx_writer`.
- **Public API (`ProcessSettings`)**: 6 new fields —
  `markdown_flavor`, `effort`, `cross_page_table_merge`,
  `fallback_to_grounded`, `long_document_strategy`, `style_map`.
- **Pipeline orchestration**: `localdeepl.plugin` entry-point
  (like Markitdown's `markitdown.plugin`); multi-stage threaded
  pipeline pattern from Docling.
- **IR**: round-trip test for `DocumentResult`; consider a
  lossless variant (Docling `DoclingDocument` / Marker `Schema`
  as references).

## Source conflicts to remember (not silently resolved)

- Azure `prebuilt-layout` Markdown uses HTML tables + LaTeX +
  `<!--PageBreak-->` (not GFM). Friction for RAG pipelines.
- Firebase AI Logic `analyze-documents` 20 MB inline vs Gemini
  API general 100 MB (Jan 12 2026 blog). Different products on
  top of the same model.
- Gemini PDF max pages: 1,000 (Developer API) vs 3,000 (Vertex
  AI doc-understanding tables — current source of truth).
- LiteLLM proxy flattens Azure `prebuilt-layout` Markdown
  response (bug #25687) — LiteLLM, not Azure.
- `datalab-to/chandra` (Marker's next-gen model) 404 on README
  fetch — likely private or renamed.
- `pymupdf_layout` license terms not fully public — needs
  deeper check before any legal positioning.
- `marker/parallel.py` does not exist in the current repo;
  orchestration lives in `marker/converters/__init__.py` via
  `BaseConverter.resolve_dependencies` + `initialize_processors`.
